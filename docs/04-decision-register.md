| S4.2 style guide (approved 2026-11-22) | (1) **Sections:** every heading (outline level 0–8, from the paragraph or its style's `basedOn` chain; level 9 = body) starts a section; text before the first heading is the preamble section; each hash includes the ancestor heading path, which is rendered with an included section. ## Unresolved technical risks

1. Model accuracy unmeasured — the verified reference set is very small; false positives on correct house-style terms are the biggest scoring risk.
2. Anchor-mismatch and ambiguity rates unknown until S5 (model may paraphrase anchors → correct findings rejected);
   the resolver itself is tested, the model's anchor quality is not.
3. Quote heuristics are tested (Q-01…Q-21, classification table, guard, nested propagation) but intentionally
   coverage-reducing; the loss rate on real text is unmeasured (S5). Known conservative losses: rule S protects to
   the last candidate closer (`‘dogs’ and the boys … cats’`) and `’` before `”` is
   ambiguous (digit–letter `’`, e.g. `1950’s`, is an apostrophe since S4.8e), German `„…“` protects to the paragraph end.
4. Grapheme clusters approximated with stdlib (exact only with `regex` package).
5. Verifier shares the expat library with the mapper (different code path).
6. Prompt-cache hit and cost unmeasured.
7. Schedule: S1–S2 ≈ one full day.
8. Memory at the input cap: a 10 MiB input took ~15.8 s with a ~1.1 GB peak working set in S1 alone; through the
   full S2 path (scan → prepare → render → verify) 28.9 s / 1.25 GB with 1,639 annotations and 47.9 s / 2.07 GB with
   327,676 annotations (measured 2026-11-21). Optimisation deferred; **not production-approved for near-cap inputs**.
9. Worst-case overlap cost: `select_disjoint` visits every overlapping pair, so k annotations that all overlap each
   other in one paragraph cost O(k²) (4,000 such annotations: 14.7 s). Since S3 the 30 raw-findings cap per
   paragraph bounds k ≤ 30 on the resolver path. Rejection de-duplication is O(k²) only for values that never equal
   themselves (e.g. NaN).
10. No automated guard against performance regressions (a timing test would be flaky without a timeout plugin);
    scaling is covered by measurements only.
11. Hypothesis runs are not seeded: each run explores new cases (this found the verifier gap in S2.6), at the cost of
    a rare failure on a newly discovered case.
12. S1 `scan()` slows down sharply when one paragraph contains very many nested `<p>`: 25.6 s for a 215 KiB document
    with 20,000 nested `<p>` in one paragraph (measured during S3.3; S3's `analyse_document` took 0.23 s on it).
    Likely quadratic in S1; not investigated or changed (open item).
13. The lower-level `resolve_findings(..., quotes=None)` applies no quotation protection. Mitigation: documented as
    a building block only; production code uses `resolve_document` (no-bypass regression tests and mutants).
14. Mutation testing is done with hand-written mutant sets in scratch scripts outside the repository (not part of
    the suite); it shows the tests detect the listed faults, not that no undetected fault exists.
